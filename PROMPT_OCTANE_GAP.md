## Цель сессии: реальные цифры Octane

Микроядра (`otter-engine-benchmark kernel`) уже на 1,5–3x от node, а
реальная нагрузка отстаёт в 8–200 раз. Улучшения микроядер больше не
считаются результатом. **Результат — рост score Octane по сьютам.** Каждый
срез обязан сдвигать score хотя бы одного сьюта Octane (или чинить
зависание/падение сьюта); в отчёте и коммите — score до/после.

Baseline на HEAD `fc08858f` (Apple M1, release,
`benchmarks/results/octane-baseline-2026-09-26/octane-fc08858f.log`):

| Сьют | node | otter | разрыв |
|---|---:|---:|---:|
| deltablue | 127714 | 612 | 209x |
| crypto | 60413 | 313 | 193x |
| regexp | 13391 | 176 | 76x |
| earley-boyer | 101860 | 1987 | 51x |
| raytrace | 95607 | 1949 | 49x |
| richards | 47340 | 1111 | 43x |
| splay | 60826 | 2395 | 25x |
| navier-stokes | 39771 | 4908 | 8x |
| pdfjs | — | 673 | node/bun сами падают |
| mandreel | 83596 | **зависание** | >25 мин CPU |
| gbemu, code-load, box2d, zlib, typescript | не измерены | | |

Разрыв такого масштаба означает не «медленный JIT», а то, что JIT на этих
программах почти не работает: отказ компиляции целой функции из-за одного
опкода, шторм деоптов, откат в интерпретатор, generic-вызовы вместо
direct, мегаморфные сайты, GC. Ищи именно это.

## Порядок работы

1. **Старт.** `git status`, `git log -3 --show-signature`: `main`, чистое
   дерево, HEAD не старше `fc08858f`. Чужие незакоммиченные изменения живой
   сессии не трогать. Прочитай `CLAUDE.md`, `AGENTS.md`, memory-заметку
   `session_2026_09_25b_wave.md`. Проверь место: `df -h /System/Volumes/Data`;
   при < 30 GB удали `target/*/deps/*.rcgu.o` и `target/*/incremental`
   (всё пересобирается).
2. **Первый срез — зависание mandreel и неработающий `--timeout`.**
   `otter --timeout 300 run …` крутился 25+ минут. Две ошибки, чинить обе:
   - таймаут CLI обязан прерывать исполнение в любом tier'е (interrupt
     доходит до backedge-poll в Template и Machine, до долгих нативных
     циклов — проверь, где он теряется);
   - сам mandreel: найди цикл (`sample <pid>`, `--jit-events`), сверь с
     `--interpreter` — это баг корректности или патологическая
     производительность.
3. **Триаж каждого сьюта (быстро, до правок).** Для каждого сьюта:
   - score в трёх режимах: `--interpreter`, `--jitless` (Template),
     по умолчанию (tiered). Если tiered ≈ jitless, оптимизатор ничего не
     даёт; если jitless ≈ interpreter, Template отказывается компилировать.
   - `--jit-events=file`: посчитай `compileFinished` с отказами (причина,
     опкод), `bail`/deopt по `exitReason` и функциям, `directCallPlan`
     rejected по причинам, мегаморфные property-сайты.
   - `sample <pid>` 10 с: доля интерпретатора, рантайм-стабов, GC,
     компилятора.
   Сведи в одну таблицу «сьют → главная причина → оценка выигрыша» и
   атакуй самую дешёвую причину с самым большим эффектом. Общие причины
   (одна дыра на несколько сьютов) — в первую очередь.
4. **Цикл среза:** причина → чистое исправление механизма → score
   затронутых сьютов до/после → лёгкая валидация → коммит → следующий.

Запуск одного сьюта с жёстким потолком (macOS без `timeout`):
```bash
perl -e 'alarm shift; exec @ARGV' 300 target/release/otter run <files…>
```
Сборка сьюта повторяет `benchmarks/run-octane.sh`: `base.js`, файлы
сьюта с `print(` → `console.log(`, затем драйвер из `run.js` без `load(`.
Сделай `scripts/dev/octane1.sh <suite> [mode]`, печатающий score.

## Измерения (быстрые)

- Score сьюта: 3 прогона, медиана; до/после на одном бинарнике-паре
  (`bin/before` = сборка предыдущего коммита, копируй перед правками).
- Микроядра — только как контроль регрессий раз в несколько срезов, не как
  цель.
- Во время замеров не гонять сборки и тесты. `uptime` в отчёт.
- Отчёт среза: `benchmarks/measurements/<дата>-<срез>.md` — причина,
  изменение, таблица score до/после, LOC. Сырые логи —
  `benchmarks/results/<срез>/` (ignored).

## Валидация (облегчённая, но обязательная)

На каждый коммит:
1. Фокусные runtime-тесты затронутых подсистем на AArch64 при
   `OTTER_GC_STRESS` unset и 1:
   `bash scripts/dev/jitset.sh aarch64 unset 1`
   (список бинарей — `jit_set.txt` рядом; полный прогон обеих архитектур,
   test262 и gate — `validate.sh <tag>`, секции через `EXTRA_SECTIONS`,
   уровни через `LEVELS_A` / `LEVELS_X`; профиль JIT-регионов —
   `regionprof.py`).
2. `cargo test -p otter-jit --lib machine` (AArch64).
3. Targeted Test262 затронутых разделов на AArch64, один runner за раз.
4. `git diff --check` и
   `CARGO_INCREMENTAL=0 CARGO_BUILD_JOBS=2 bash scripts/gate.sh`.

Каждые 3 коммита или в конце сессии — полный прогон: Rosetta
(`--target x86_64-apple-darwin`), стресс 16/4/1, test262 на x86. Упало —
чинить сразу.

Никогда: `cargo test --workspace`, широкий node-compat, параллельные
test262-раннеры.

## Правила архитектуры (без исключений)

- Активный стек: otter-gc → otter-vm → otter-runtime → product crates.
  Внутренние контракты меняй на месте, обновляя всех потребителей в одном
  коммите. Никаких compatibility-путей, feature flags, env-переключателей,
  `thread_local!`, bridges.
- Меняй механизм, не подгоняй под бенчмарк; нагрузку/таймауты/assertions
  не ослабляй. Эвристики — только со ссылкой на то, как это делают
  V8/JSC/SM.
- GC: moving-значения укоренены на любом аллоцирующем пути; барьеры
  old→young; сырые указатели на движущиеся объекты не кешируются.
- Выход/деопт после совершённого эффекта запрещён; промах выполняет
  операцию ровно один раз; спекуляции самокорректируются.
- Любой найденный баг — наш: чинить на месте, без откатов «проверить, было
  ли до меня», и двигаться дальше. Кривые тесты чинить или удалять быстро,
  не тратить на них сессию.
- Модули с новым/изменённым поведением — точные `//!`-доки. JS разбирать
  только AST (oxc). Поиск — fff/rg.

## Ловушки (проверено)

- zsh не делит `$VAR` по словам: циклы только через `bash -c` / скрипты.
- Все файлы — в репозитории (`scripts/dev/`, `benchmarks/results/` для
  сырых логов), не в `/private/tmp` и не в scratchpad.
- Не редактируй файлы, которые фоновая валидация ещё будет компилировать;
  свою правку отложи патчем в `benchmarks/results/` (ignored).
- `target/` разрастается до 70+ GB → ENOSPC посреди сборки.
- `otter-engine-benchmark` и `otter` собираются отдельно: пересобирай тот,
  которым меряешь. CLI: `--jit-events=path` (с `=`), `--jit-artifacts=dir`,
  `--jitless`, `--interpreter`, `-p` принимает текст, не файл.
- Под Rosetta x86 Template теперь покрывает все TemplateOp; расхождение
  arm64/x86 — баг.
