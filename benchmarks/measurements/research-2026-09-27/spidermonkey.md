## 1. One environment object per scope activation, not one cell per binding (earley: 110.9M cells, 10.2M closures)
1. **Source:** `js/src/vm/EnvironmentObject.h` ([SMDOC] Environment Objects; `CallObject`, `BlockLexicalEnvironmentObject`, `ENCLOSING_ENV_SLOT`, `CALLEE_SLOT`); `js/src/vm/Opcodes.h` (`GetAliasedVar`, operands `hops`, `slot` = `EnvironmentCoordinate`); `js/src/jit/BaselineCodeGen.cpp` `BaselineCompilerCodeGen::initEnvironmentChain`; `js/src/jit/WarpBuilder.cpp` `build_GetAliasedVar`, `buildEnvironmentChain`.
2. **Work eliminated:** SpiderMonkey keeps "Local bindings that aren't closed over or dynamically accessed" in stack slots (Opcodes.h). It stores all other ("aliased") bindings of a scope in one EnvironmentObject. EnvironmentObject.h: "For block and function scopes where all bindings can be stored in stack slots, nothing is allocated in the heap". A `JSFunction` holds exactly one env pointer (`JSFunction::offsetOfEnvironment`). With k captured bindings and m inner closures the cost is 1 env plus m functions. Otter pays k cells plus m closures, and each closure carries its own capture list (inline in the closure tail since Otter commit 76aa818d). Closure creation in SpiderMonkey copies no capture list.
3. **Hot/cold:** `GetAliasedVar` does `hops` loads of `[env+ENCLOSING_ENV_SLOT]` (unboxed), then one load of a fixed slot (`EnvironmentObject::nonExtensibleIsFixedSlot`), or `slots_`+index past that. In the **Baseline Compiler** prologue, NamedLambda and CallObject come from inline `createGCObject` on templates: store the enclosing env and the callee, then set `HAS_INITIAL_ENV`. The VM call `jit::InitFunctionEnvironmentObjects` runs only on the fail path. There are two exceptions. The Baseline *Interpreter* always makes that VM call when `NeedsFunctionEnvironmentObjects` is set. The Compiler also takes the VM call for realm-independent (self-hosted cache) code.
4. **Invariants:** The env layout (template) is fixed per Scope, and hops/slot are static. The debugger can reconstruct unaliased bindings (`EnvironmentIter`, `DebugEnvironmentProxy`).
5. **GC/deopt:** An env is an ordinary NativeObject, so it can be allocated in the nursery. `emit_SetAliasedVar` does a pre-barrier plus a post-barrier (`branchValueIsNurseryCell`, `postBarrierSlot_`). Warp sets the env slot only after the env is complete, so that "bailout doesn't see a partial environment".
6. **Cost:** About a 24 B header, plus reserved slots, plus 8 B per binding, rounded up to the GC size class, once per scope. A CallObject has 2 reserved slots (enclosing env, callee). Lexical and block envs have 4, because `DisposableEnvironmentObject` adds a dispose-stack slot and the lexical class adds a scope/this slot. The downside is that any live closure keeps every aliased binding of the scope alive. Per-binding cells keep only what each closure captured.
7. **AOT:** Coordinates are compile-time constants, and there is one template shape per Scope (static data or startup materialization).
8. **JS limits:** Sloppy direct `eval` and `with` force dynamic lookup ("can't be used when there's a dynamic scope"). Per-iteration `let` needs a fresh block env (`build_FreshenLexicalEnv`). Mapped `arguments` aliases formals through the CallObject.
9. **Otter experiment:** On earley, count per activation how many UpvalueCells it allocates and plot the histogram. The ratio of 110.9M cells to 10.2M closures suggests about 10 per closure. If the mean is much greater than 1, prototype `EnvRecord{enclosing, slots[k]}` with the closure holding one ref. Expected result: cell allocations fall to the number of activations with captures, and GC share falls. The idea is refuted if most activations capture 1 binding.

## 2. Inline nursery allocation plus AllocSite pretenuring
1. **Source:** `js/src/jit/MacroAssembler.cpp` `bumpPointerAllocate`, `createGCObject`, `updateAllocSite`; `js/src/gc/Pretenuring.h` `AllocSite` (Unknown/LongLived/ShortLived; `NormalSiteAttentionThreshold = 200`, `UnknownSiteAttentionThreshold = 30000`); `js/src/gc/Pretenuring.cpp` `AllocSite::processSite`, `updateStateOnMinorGC`, `invalidateScript`, `MaxInvalidationCount = 5`; `js/src/gc/Nursery-inl.h` `Nursery::tryAllocateCell` (`NurseryCellHeader`); `js/src/jit/CodeGenerator.cpp` `visitLambda`, `visitNewCallObject`; `js/src/jit/CacheIR.cpp` `LambdaIRGenerator::tryAttachFunctionClone`.
2. **Work eliminated:** Closures, envs, `this` objects and literals are allocated inline with no runtime call. Short-lived objects die in scavenges. Only sites with a measured high promotion rate skip the nursery.
3. **Hot path:** `mov t,&pos; ld r,[t]; add r,size+8; cmp [t+endOff],r; jb fail; st [t],r; sub r,size; st [r-8],site|kind`, then template init (shape, `slots_`, `elements_`, slots). Baseline counts per site (`updateAllocSite`, including `ICScript::offsetOfEnvAllocSite` for envs). Warp uses the catch-all `Optimized` site and bakes `initialHeap` from the site state (`WarpOracle`, `allocSiteInitialHeapField`).
4. **Invariants:** Every nursery cell is preceded by a header word holding the site and trace kind. Whether nursery allocation is enabled for a kind is a codegen constant ("we discard JIT code when this changes"). A tenured-heap `MLambda` storing a nursery env takes an explicit post-barrier (`visitLambda`).
5. **Policy/deopt:** At each minor GC, a site is evaluated only if it made more than 200 nursery allocations since the previous minor GC. The counts are then reset. Unknown catch-all sites need 30,000. From Unknown, a promotion rate of 0.9 or more moves the site to LongLived (pretenured), and a lower rate moves it to ShortLived. ShortLived returns to Unknown on a high rate, and LongLived returns to Unknown on a low rate. ShortLived→LongLived therefore never happens directly. *Only* the Unknown→LongLived transition invalidates the owning Ion script. After 5 such invalidations the site is pinned at Unknown and keeps allocating in the nursery. Separately, a zone-level check marks high nursery survival when more than 60% of the nursery is promoted and the Optimized catch-all site has at least 10,000 promotions.
6. **Cost:** 8 B per nursery cell and a few words per allocating bytecode site.
7. **AOT:** `ImmPtr(zone->addressOfNurseryPosition())` is baked as an absolute address, so AOT would need it from a context register. Baseline keeps site pointers in the ICScript (data), so the code stays shareable. Warp's heap decision depends on the profile, so AOT should default to the nursery or read a site word at runtime.
8. **JS limits:** None semantically. The stub is disabled when an allocation-metadata builder (devtools) is active. *[not re-verified in this pass]*
9. **Otter experiment:** Otter now allocates closures and cells in OLD space through Rust calls. Add a young-space bump path for both in Template and Machine, with per-site promoted counters. Measure earley GC share (about 30% now) and zlib RSS. If these sites promote at 0.9 or more, the gain must come from card 1. *[Otter-side note: a policy-only pilot that moved local binding cells to the existing generational allocator was measured and rejected on 2026-09-27. It cost +6.27% instructions on earley, and RSS moved by less than 0.3%; see `benchmarks/measurements/2026-09-27-young-bindings.md`. That pilot kept Rust-call allocation and had no inline bump path or per-site pretenuring, so it does not test this card's mechanism. Do not repeat it as-is.]*

## 3. Scalar replacement of CallObject together with MLambda (Warp)
1. **Source:** `js/src/jit/ScalarReplacement.cpp`: `IsOptimizableObjectInstruction` (NewObject, NewPlainObject, NewCallObject, NewIterator, NewBoundFunction), `IsObjectEscaped`, `IsLambdaEscaped`, `ObjectMemoryView::functionForCallObject`, `visitFunctionEnvironment`, `visitLambda` (`setIncompleteObject`). `js/src/jit/Recover.h`: `RLambda`, `RFunctionWithProto`, `RNewCallObject`, `RObjectState`. `js/src/jit/TrialInlining.h` ([SMDOC] Trial Inlining).
2. **Work eliminated:** The replacement applies when the CallObject is used by fixed/dynamic slot loads and stores, by lambdas, and by non-escaping wrappers of itself: shape/class guards, `CheckIsObj`/`Unbox`, and phis whose operands are all the same object. Each lambda (`MLambda` or `MFunctionWithProto`) may be used only by `GuardToFunction`, `GuardFunctionScript` (matching script), `FunctionEnvironment` (an inlined callee reading its env), or recoverable resume-point operands. When that holds, both the env and the closure vanish, and captured variables become SSA values.
3. **Hot/cold:** The hot path has zero instructions. On bailout, `RNewCallObject`, `RObjectState` and `RLambda` materialize the objects.
4. **Invariants:** "only supports objects which are not changing shape". Every use must be classified. The lambda is marked incomplete so that recovery rebuilds it on the recovered env.
5. **GC/deopt:** Recovery allocates. If the stack is introspected, "any use of recover instruction must lead to an invalidation of the code" (Recover.h).
6. **Cost:** A linear use scan per candidate plus one `EmulateStateOf` dataflow pass per replaced object.
7. **AOT:** It requires the callee to be inlined into the same graph. SpiderMonkey gets there with trial inlining, which gives each call site its own ICScript. An AOT compiler would need a closed-world or PGO answer to "`map` is the builtin".
8. **JS limits:** It does not help closures that escape to the heap, such as Scheme-style continuations in earley. Cards 1 and 2 dominate there.
9. **Otter experiment:** Otter has partial escape but per-binding cells, so each cell is a separate candidate. On ts and earley Machine code, count the MakeClosure results that reach only inlined calls. Also count how many cells survive because one sibling cell escapes. Compare against a single per-scope env candidate.

## 4. CacheIR: one IC language for all tiers
1. **Source:** `js/src/jit/CacheIR.h` ([SMDOC] CacheIR); `js/src/jit/CacheIROps.yaml` (fields `shared`, `transpile`, `cost_estimate`; at this commit 468 ops, 460 `transpile: true`, 390 `shared: true`); `js/src/jit/WarpOracle.cpp` `WarpScriptOracle::maybeInlineIC`; `js/src/jit/WarpCacheIRTranspiler.cpp` (e.g. `emitGuardShape` → `MGuardShape`); `js/src/jit/JitScript.h` ([SMDOC] JitScript).
2. **Work eliminated:** IC semantics are written once, by IRGenerators. Baseline compiles CacheIR to stub code that is shared across stubs ("stubs that have the same CacheIR … will have the same Baseline stub code", with data kept in the ICStub). Ion ICs bake the data in. Warp transpiles the single active stub into MIR, so the optimizing tier has no second property/call specialization and no separate feedback format. `TryFoldingStubs` folds shape-polymorphic stubs into `GuardMultipleShapes`.
3. **Hot path (Warp, monomorphic get):** `cmp [obj+shape],imm; jne bail; ld r,[obj+off]`. GVN and LICM then merge and hoist the guards.
4. **Oracle rules:** A cold IC (fallback never entered, no stubs) gets a `WarpBailout` snapshot, and so does a stub whose invalidating fuse is already popped. An Ion IC is left in place in these cases:
   - the fallback was entered but has no stub;
   - `hasFailures()`;
   - any `transpile: false` op;
   - several stubs with a nonzero entered count. The exception is ops that support polymorphic type data when the fallback was never entered; there `maybeInlinePolymorphicTypes` may still transpile.
5. **GC/deopt:** Stub fields are traced through `CacheIRStubInfo`. The snapshot replaces nursery pointers with indices (`WarpObjectField`, `MNurseryObject`, [SMDOC] Warp Nursery Object/Value support), so off-thread compilation survives minor GCs. A failed transpiled guard raises `BailoutKind::TranspiledCacheIR`, and the script is invalidated once bailouts are frequent (`frequentBailoutThreshold` default 10). The transpiler asserts at most one effectful op per stub (`addEffectful`), and that op carries a resume point.
6. **Cost:** Stub chains per IC; stub data is copied into the snapshot on the main thread.
7. **AOT:** CacheIR is serializable, typed data (shapes, slots, ids). Shared-code stubs whose data lives in the stub are relocation-free. Profile-specialized code needs shape identities that exist only at runtime.
8. **JS:** It covers getters and setters (`CallScriptedGetterResult`, `CallScriptedSetter`), Proxy, arguments, dense and typed elements, and the megamorphic case (`MegamorphicLoadSlotResult`).
9. **Otter experiment:** Otter's CacheIR is interpreter-only, and Template and Machine each lower access and calls on their own. Transpile interpreter stubs for Get/Set/Call into Machine HIR on ts-fixed and mega_method. Measure instructions, and count how much lowering code is deleted and how many tier-divergence bugs disappear.

## 5. The Baseline Interpreter is the Baseline JIT codegen with a different Handler
1. **Source:** `js/src/jit/BaselineCodeGen.h` `BaselineCompilerHandler`, `BaselineInterpreterHandler`; `js/src/jit/BaselineCodeGen.cpp` `BaselineInterpreterGenerator::emitInterpreterLoop`; `js/src/jit/BaselineJIT.h` `BaselineInterpreter`; `js/src/jit/BaselineFrame.h` (`RUNNING_IN_INTERPRETER`, `interpreterPC_`, `interpreterICEntry_`, `REALM_INDEPENDENT`). *[spot-checked: symbols confirmed]*
2. **Work eliminated:** Each `emit_<Op>` is written once, as a template over the handler. The interpreter and the JIT share the frame layout and the ICScript, so tier-up at a loop head is a jump, and Ion bailouts land in the interpreter (`bailoutPrologueOffset_`) with no frame conversion.
3. **Hot path:** Each op ends with threaded dispatch: `add pc,len; ldrb op,[pc]; jmp [table+op*8]`. IC ops also bump `interpreterICEntry_`. *[instruction sequence not re-verified]*
4. **Invariants:** The interpreter-only frame fields are valid only under `RUNNING_IN_INTERPRETER`. IC entries are laid out in bytecode order.
5. **GC/deopt:** Frame walking and safepoints are the same for both tiers. The debugger uses toggled jumps and traps.
6. **Cost:** One generated JitCode per runtime and no per-script code before baseline compilation.
7. **AOT:** The interpreter is realm-independent generated code and could be shipped prebuilt. `realmIndependentJitcode()` (the pref `experimental_self_hosted_cache` plus `selfHosted`) makes Baseline code for self-hosted scripts shareable.
8. **JS limits:** None.
9. **Otter experiment:** On fib (4.0x) and after deopts, measure the instructions spent converting Rust-interpreter frames to and from Template frames. If they are significant, generate interpreter op bodies from the Template emitter.

## 6. Prototype in the Shape, shape teleporting, Watchtower and MegamorphicCache (mega_method 2.5x, ts)
1. **Source:** `js/src/vm/Shape.h` ([SMDOC] Shapes: a shape "stores and implies … JSClass, Realm, prototype" through `BaseShape`); `js/src/jit/CacheIR.cpp` `GeneratePrototypeGuards` ([SMDOC] Shape Teleporting Optimization), `ShapeGuardProtoChain` ("relies on shape implying proto"); `js/src/vm/Watchtower.h`; `js/src/vm/Caches.h` `MegamorphicCache` (`NumEntries = 1024`, `bumpGeneration`).
2. **Work eliminated:** A proto-chain load at any depth costs 2 shape guards, one on the receiver and one on the constant holder. Megamorphic sites do a (shape, key) → (hops, slot) cache hit instead of a lookup walk.
3. **Hot path:** `cmp [recv+shape],S1; jne; cmp [holderK+shape],S2; jne; ld [holderK+slot]`. Megamorphic: hash the shape and key, compare shape, key and generation, follow `hops` protos, then load.
4. **Invariants:** Shadowing on a prototype or mutating a prototype's `[[Prototype]]` reshapes the affected objects (`ReshapeForShadowedProp`, `ReshapeForProtoMutation`). Once `InvalidatedTeleporting` is set on the holder, a shape guard is emitted for each proto between the receiver and the holder. Watchtower fires only for objects with specific ObjectFlags on the Shape. The cache is invalidated by generation bumps (driven by Watchtower on prototype mutation) and on each major GC.
5. **GC/deopt:** No deopt. A guard failure goes to the IC fallback (in Warp, a transpiled-guard bailout).
6. **Cost:** Proto-in-shape multiplies shapes. PropMaps (8 keys each, `CompactPropMap`, shared prefixes) offset part of that.
7. **AOT:** Shapes are runtime identities, so code must load expected shapes from per-site data.
8. **JS limits:** `setPrototypeOf` and `__proto__` writes pay for a reshape. Proxies use `ProxyShape`. Dictionary objects get a new shape on every mutation. *[ProxyShape/dictionary claims not re-verified]*
9. **Otter experiment:** Otter's shapes lack the prototype. Add it to the shape key, then count guard instructions per method call on mega_method and ts-fixed. Separately, add a generation-invalidated global (shape, key) cache and measure its hit rate.

## 7. Fixed slots sized from `this.x =` counts, with the `this` shape baked into the call IC (ast_ctor 9.6x)
1. **Source:** `js/src/vm/NativeObject.h` ([SMDOC] NativeObject layout; `MAX_FIXED_SLOTS` = `JS::shadow::NativeObject::MAX_FIXED_SLOTS` = 16); `js/src/frontend/BytecodeEmitter.cpp` `emitAssignmentOrInit` (`propertyAdditionEstimate++` on `this.foo =`, plus `numMemberInitializers`); `js/src/vm/SharedStencil.h` `propertyCountEstimate`; `js/src/vm/JSFunction-inl.h` `JSFunction::getAllocKindForThis`; `js/src/vm/PlainObject.cpp` `ThisShapeForFunction`; `js/src/jit/CacheIR.cpp` `CallIRGenerator::emitCallScriptedGuards` → `metaCreateThis(...)`.
2. **Work eliminated:** Constructed objects get enough fixed slots up front, up to the 16-slot fixed-slot cap. Within that cap there is no `slots_` malloc or growth; properties beyond 16 still go to dynamic slots. The call IC guards the `newTarget` shape and the identity of its `.prototype` slot, and `MetaCreateThis` (`cost_estimate: 0`) lets Warp "create the |this| object before transpiling the call". Field inits become `AddAndStoreFixedSlot` transitions with known shapes, and the object can be scalar-replaced when it does not escape.
3. **Hot path:** Bump-allocate, then store the initial shape and undefined into the slots. Each field is `cmp shape; jne; st slot; st newShape`.
4. **Invariants:** The same shape implies the same fixed-slot count. The estimate counts syntactic `this.foo =` assignment and init *sites* per function body (a repeated name counts again), plus class member initializers. It is accumulated as a saturating uint8 and stored in a `uint16_t` field. The kind is `GetGCObjectKind(max(default kind slots, estimate))`, which caps at 16 fixed slots. `this[x] = …` is not counted.
5. **GC/deopt:** The nursery with a per-call-IC AllocSite.
6. **Cost:** An overestimate wastes slots (bounded by the 16-slot cap). I found no slack tracking comparable to V8's (not verified exhaustively).
7. **AOT:** The estimate is a pure frontend fact, so AOT can use it.
8. **JS:** Derived-class constructors (`constructorNeedsUninitializedThis`) and exotic newTargets fall back.
9. **Otter experiment:** On ast_ctor, log per constructor the final property count, the inline capacity, and the number of slot-vector growths. Then add the frontend estimate and re-measure.

## 8. Bailouts, recover instructions, and recompilation policy per bailout kind
1. **Source:** `js/src/jit/Bailouts.h` ([SMDOC] IonMonkey Bailouts); `js/src/jit/Recover.h`; `js/src/jit/BaselineBailouts.cpp` `BailoutIonToBaseline`, `FinishBailoutToBaseline`; `js/src/jit/Invalidation.h` `IonScriptKey`, `jit::Invalidate`; `js/src/jit/Ion.cpp` `InvalidateActivation`. *[spot-checked: LICM and bounds-check handling confirmed in BaselineBailouts.cpp; other flag names not re-verified]*
2. **Work eliminated:** Each guard gets a tiny stub (`push id; jmp _deopt`) behind one shared trampoline. Optimized-away values are recomputed only on bailout. Each `BailoutKind` sets a script flag that disables only the optimization that failed: LICM (`setHadLICMInvalidation`), hoisted bounds checks (`setFailedBoundsCheck`), eager truncation, speculative phis, reordering. This stops bail loops without disabling the tier.
3. **Hot path:** One cmp and branch per guard.
4. **Invariants:** Each snapshot maps every Baseline slot to a register, stack slot, constant or recover instruction. Inlined frames are rebuilt as BaselineJS frames joined by BaselineStub frames that resume in fallback ICs. OSI patches the return addresses of invalidated frames. The first LICM bailout takes `NoAction` (the IonScript records `LICMState::Bailed`). If the baseline fallback is not hit before the next one, that bailout sets `hadLICMInvalidation` and invalidates.
5. **Exceptions:** "Ion doesn't implement `catch` or `finally`", so it uses `ExceptionHandlerBailout`.
6. **Cost:** Compact snapshot and recover buffers per IonScript.
7. **AOT:** It needs a lower tier in the binary (SpiderMonkey's model) or generic slow paths. Snapshots are position-independent data.
8. **JS limits:** None.
9. **Otter experiment:** Tabulate Machine deopts by cause on earley and ts, then replace coarse throttling with per-cause flags. Measure deopts and instructions.

## 9. PUNBOX64 value format
1. **Source:** `js/public/Value.h` ([SMDOC] JS::Value Boxing Formats; `JSVAL_TAG_SHIFT 47`, `JSVAL_TAG_MAX_DOUBLE = 0x1FFF0`). *[spot-checked: constants and tag-ordering rationale confirmed]*
2. **Work eliminated:** A double is a bit-cast, and every bitstring at or below `0xfff8…` is a double (one compare). The shifted Object, String and Symbol tags are "each a contiguous run of set bits" that AArch64 encodes as logical immediates, so boxing and tests need no materialized constant. Object and Null differ by one bit. The number tags are lowest and the GC tags highest, so `isNumber` and `isGCThing` are single compares.
3. **Hot path:** An ARM64 tag test is `eor` or `tst` with an immediate, and unboxing is one mask or xor.
4. **Invariants:** Pointers must fit in 47 bits (`js::gc::MapAlignedPagesRandom`), and NaNs are canonicalized.
5. **GC:** Pointers are raw, with no base add.
6. **Cost:** 8 B per heap pointer.
7. **AOT:** The format is an ABI constant.
8. **JS limits:** None.
9. **Otter:** Keep the 32-bit cage offsets, since they matter for RSS (zlib 795 MB). Audit Otter's tag masks for ARM64 logical-immediate encodability, and count `base+offset` materializations in the hot loops of crypto and zlib.

## 10. Stencil/XDR and self-hosted builtins as the portable compile unit
1. **Source:** `js/src/frontend/Stencil.h` ([SMDOC] Script Stencil); `js/public/experimental/JSStencil.h` `CompileGlobalScriptToStencil`, `InstantiateGlobalStencil`, `EncodeStencil`, `DecodeStencil`; `js/src/frontend/Stencil.cpp` `CompilationStencil::instantiateStencils`, `delazifySelfHostedFunction`; `js/src/frontend/StencilXdr.cpp` `JS::GetScriptTranscodingBuildId`; `js/src/vm/SelfHosting.cpp` `JSRuntime::initSelfHostingStencil`, `JSRuntime::delazifySelfHostedFunction`, `JS_INLINABLE_FN` (86 uses); `js/src/builtin/Array.js` `ArrayMap` + `SetIsInlinableLargeFunction(ArrayMap)`. *[spot-checked: `GetScriptTranscodingBuildId`, the 86 `JS_INLINABLE_FN` uses and `SetIsInlinableLargeFunction(ArrayMap)` confirmed; the other Stencil symbols and quotes not re-verified]*
2. **Work eliminated:** Parsing and emission happen once, with no GC or realm involved ("indices over pointers and vectors instead of graphs"), and the result can be instantiated into any realm. XDR can be borrowed straight from the buffer (`borrowBuffer`, `usePinnedBytecode`: "directly use bytecode from the XDR buffer without copying"). There is one self-hosted stencil per process, shared by worker runtimes (`parentRuntime`), with lazy per-realm functions that can be relazified. Builtins written in JS go through the same ICs and Warp, so callbacks inline into `map`.
3. **Hot/cold:** Instantiation is the cold path; there is no reparse.
4. **Invariants:** XDR is tied to the build id, with no format versioning (consistent with Otter's rule). ParserAtoms are not GC things, and a CompilationStencil is immutable and refcounted.
5. **GC:** A stencil holds no GC pointers.
6. **Cost:** Lazy functions are delazified later and merged (`CompilationStencilMerger`).
7. **AOT:** Stencil is SpiderMonkey's only persistent artifact, and it is bytecode, not machine code. For Otter, a GC-free, index-based IR of this kind is the natural shared input for both JIT and AOT, and only shape and atom indices would need relocation.
8. **JS:** `eval` produces stencils at runtime.
9. **Otter experiment:** On a callback-heavy benchmark, compare the Rust-native `Array.prototype.map`/`forEach` against self-hosted JS versions that inline into Machine.

## What SpiderMonkey does not spend that Otter spends
- **A heap cell per captured binding.** SpiderMonkey allocates at most one env per scope activation, and none if nothing is captured.
- **An old-space allocation through a runtime call per closure or cell.** SpiderMonkey bump-allocates in the nursery inline. It pretenures a site only after measuring a promotion rate of 0.9 or more, and re-invalidates code for that at most 5 times per site.
- **Re-deriving property and call semantics in each tier.** SpiderMonkey has one CacheIR generator, and Warp transpiles its output.
- **A guard per prototype on proto loads.** The shape implies the proto, and teleporting brings any depth down to 2 guards.
- **Slot-vector growth for constructed objects.** SpiderMonkey sizes fixed slots from `this.x =` counts, up to 16 fixed slots.
- **Materializing non-escaping env, closure, arguments and rest objects.** SpiderMonkey scalar-replaces them and recovers them on bailout.
- **Coarse throttling after bail loops.** SpiderMonkey's per-bailout-kind flags disable only the failing optimization.
- **Reparsing builtins or scripts at startup.** SpiderMonkey uses a build-id-keyed, borrowable Stencil XDR and one shared self-hosted stencil.
- **Cage-base adds on pointer decode.** SpiderMonkey avoids them by paying 2x pointer width, so this is a trade rather than a pure win.
